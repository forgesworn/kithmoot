# Verified updates

How each KithMoot client finds and installs a new version, and why a
compromised download server cannot use that path to install anything.

## Who updates what

| Client | Updated by | What it trusts |
|--------|-----------|----------------|
| Mac (Apple Silicon) | Squirrel.Mac, `desktop/updater.mjs` | Apple Developer ID code signature, checked against the running app's signing requirement |
| Linux `.deb` | apt | The KithMoot archive key in the package's `Signed-By` |
| Windows ZIP | `desktop/archive-updater.mjs` | The signed update manifest, below |
| Linux tarball | `desktop/archive-updater.mjs` | The signed update manifest |
| Android from Zapstore | Zapstore | Zapstore's signed release events, and Android's own signing-certificate check |
| Android from the downloads page | the app | The signed update manifest, and Android's signing-certificate check |
| Web app | the browser | The site's TLS certificate (the PWA is served, not installed) |

## The threat

The downloads live on one public box. Somebody who controls it can change
any file there, including `SHA256SUMS.txt`, `release.json` and
`android-release.json`. So a checksum fetched from the same place as the
download proves nothing, and neither does TLS. The apps must only accept
an update that something they already hold says is genuine.

## The signed update manifest

`site/downloads/release.json` (desktop) and `site/android-release.json`
(Android) are each signed at release time on the release machine, never on
the box. Each signature sits beside its file as `<file>.sig`.

- **Algorithm:** Ed25519. Node verifies it without dependencies, and
  BouncyCastle, already in the Android app, verifies it there.
- **Message:** `"kithmoot/v1/update-manifest\n" + label + "\n" + file bytes`,
  where the label is the file's path on the site (`downloads/release.json` or
  `android-release.json`). The signature covers the bytes exactly as served,
  so nothing is reformatted before checking, and a signature for one file
  never verifies as the other.
- **Encoding:** the `.sig` file is the 64-byte signature in base64.
- **Keys:** two public keys are built into every app (`UPDATE_KEYS` in
  `desktop/update-manifest.mjs`, and the Android equivalent). The *release
  key* signs every release. The *recovery key* is kept offline and signs
  nothing day to day. If the release key is lost or leaked, a release signed
  by the recovery key ships a new key set, and nobody is stranded.
- **Vectors:** `vectors/update-manifest.json`, regenerated by
  `vectors/generate-update-manifest.mjs`, is checked by both repositories.

An app that has verified the manifest then takes from it the download's
SHA-256 and its size in bytes, and:

1. refuses any version that is not strictly newer than the one running, so
   a replayed old manifest can at worst hold an app back, never downgrade it;
2. streams the download, counting bytes and hashing as it goes, and stops
   the moment it runs past the signed size;
3. deletes anything whose size or hash does not match, and says the update
   could not be verified;
4. only then unpacks or installs it.

A refusal at any of these steps, or Squirrel refusing a Mac update's code
signature, is flagged `unverified` and shown in the app once per run as
"Update not installed", rather than only logged: it may mean the download
server has been tampered with. Ordinary failures, such as being offline,
stay quiet and are retried.

On Android the installer then also requires the new APK to be signed by the
same certificate as the installed app (or its rotation lineage), and the app
checks that itself first so a mismatch never reaches the person.

## Desktop: Windows ZIP and Linux tarball

`createArchiveUpdater` checks 30 seconds after launch and then hourly. A
verified archive is unpacked into `<install folder>.update-<version>` beside
the app. When the person accepts the restart, which waits for a call or
unsent work to finish, the old folder becomes `<install folder>.previous` and
the new one takes its place:

- **Linux** renames both folders in place, which a running app allows, and
  relaunches the new copy.
- **Windows** cannot move a running app's folder, so a small PowerShell
  helper (`WINDOWS_SWAP`) waits for KithMoot to exit, makes the swap,
  restores the old folder if the swap fails, and starts KithMoot again.

The next start removes the `.previous` folder and any unpacked update that
was not taken. Updates are off when the app's folder or its parent cannot be
written, such as under `Program Files`. Archives are unpacked with the system
`tar` (`%SystemRoot%\System32\tar.exe` on Windows 10 1803 and later).

## Android

See the KithMoot Android repository. A copy installed by Zapstore is left to
Zapstore, and the app only points there. A copy installed from the downloads
page downloads the APK the signed manifest names, verifies its size, hash,
package and signing certificate, and hands it to Android's package installer.

## Releasing

After the release files are updated and before committing:

```
node scripts/update-signing.mjs sign
```

This signs both manifests with the release key in `~/.kithmoot-signing/update`
and checks them against the keys the apps carry. `deploy/deploy.sh` runs
`node scripts/update-signing.mjs check` and refuses to deploy a manifest
that does not verify, and `desktop/test/update-manifest.test.mjs` fails on
one too.

## Key custody

`~/.kithmoot-signing/update/` holds `release.pem` and `recovery.pem`
(passphrase-encrypted PKCS#8), each passphrase in a mode-600 file beside it,
and the public halves. Both are backed up to Proton. The recovery key's
private half should not stay on the release machine once backed up.

To rotate: generate a new key, add it to `UPDATE_KEYS` in both apps, ship
that release signed by a key the installed apps already trust, and only then
sign with the new key.
